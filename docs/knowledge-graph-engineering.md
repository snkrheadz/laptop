## TL;DR

- **マルチエージェントの根本的弱点はコンテキストウィンドウ**: 各エージェントの
  記憶はウィンドウと共に消え、ワーカー間の情報共有をオーケストレーターの
  ウィンドウ経由で行うとワーカー数に比例して肥大化する。ナレッジグラフは
  その外側に置く共有インフラ層。
- **古典 NLP パイプライン (学習済み NER + 関係分類器 + エンティティ解決
  ヒューリスティック) は structured outputs のプロンプト列に潰せる**。
  「学習データ」に相当するのは Pydantic スキーマだけ。ドメイン適応コストが
  数週間のラベリングから数時間のプロンプトチューニングに落ちる。
- **RAG とは競合でなく補完**: RAG は単一ホップの直接検索に安くて有効。
  グラフは語彙的に似ていない複数文書の事実を連鎖させるマルチホップ推論用。
- **評価ハーネス (gold set + F1 ループ) がデモを本番に変える**。これは
  evals-for-ai-agents.md と同じ結論の別ドメイン実例。

## 1. パイプライン: 4ステージ全部 Claude API 呼び出し

| ステージ | モデル | 理由 |
|---|---|---|
| 抽出 (Extraction) | Haiku | 大量処理・スキーマ制約下。速度とコストが支配的 |
| 解決 (Resolution) | Sonnet | 矛盾する証拠の重み付け = 推論品質が支配的 |
| 要約 (Summarization) | Sonnet | 複数文書をまたぐ統合。ニュアンスが重要 |
| 問い合わせ (Querying) | Sonnet | シリアライズ済みトリプル上のマルチホップ推論 |

原則: **判断が必要な部分だけモデル、それ以外は決定論的ロジック**
(claude/CLAUDE.md §2 のモデルルーティング、/core:promote-to-code と同じ思想)。

### 抽出のポイント

- `client.messages.parse()` + Pydantic `output_format` で型付きオブジェクトが
  返る。正規表現・JSON パース・防御的チェックが全部消える。パイプラインの
  信頼性はほぼ「ステージ間インターフェースの堅牢性」で決まる。
- プロンプトの一語が precision/recall を直接制御する:
  「この文書の中心となるエンティティ**のみ**」= precision 優先。
  実測 precision 1.00 / recall 0.38–0.55 は意図的トレードオフ —
  **誤ったエンティティは誤った関係をマルチホップで増殖させる**ため、
  エージェント向けデータでは偽陽性の方が偽陰性より有害。
- 各エンティティに「この文書に根ざした一文の説明」を書かせる。これが次段の
  曖昧性解消シグナルになる ("Edwin Aldrin" = "Buzz Aldrin" を文字重複ゼロでも
  同一人物と判定できる根拠)。
- コスト: システムプロンプト + スキーマは固定なのでプロンプトキャッシュ。
  24h 遅延を許容できるジョブは Message Batches API で 50% オフ。

### 解決のポイント

- 1万件のエンティティを1プロンプトに入れない。安いシグナル (名前重複・
  埋め込み類似) で決定論的にブロック分けし、50–100件のブロック内だけで
  LLM が裁定するハイブリッド方式。
- 失敗モード2つを監視: ①未マッチ名のサイレント消失 (単要素クラスタへの
  フォールバックで防ぐ) ②過剰マージ (説明文の重複による別エンティティの統合)。

## 2. グラフがマルチエージェントで果たす3つの役割

1. **共有メモリ (orchestrator–workers)**: 各ワーカーは関連サブグラフだけを
   読み、新規エンティティ・関係を書き戻す。オーケストレーターのコンテキストは
   小さいまま。「session is not the context window」原則のマルチエージェント版。
2. **グラウンディング層 (evaluator–optimizer)**: 評価者が「それらしいか」でなく
   「グラフにそのトリプルが存在するか」で判定できる。出典エッジ付きの
   事実チェックであり、モデルの推定ではない。
3. **永続的ワールドモデル (長時間ループ)**: コンテキストフラッシュを生き延びる。
   新規文書は既存の正準集合に対して解決しエッジだけ追加 (全体再構築しない)。
   「the agent forgets, the repo does not」のグラフ版。

## 3. 問い合わせ時のコンテキスト設計

- seed エンティティから **k=2 ホップ**のサブグラフをトリプルとして
  シリアライズして渡すのが実用上のスイートスポット (k=1 は間接接続を逃す、
  k=3 以上はウィンドウを溢れさせがち)。
- 「以下のナレッジグラフ**のみ**を使って答えよ、根拠エッジを引用せよ」と
  制約する。pretraining 由来の「それらしいが検証不能な答え」を排除し、
  引用を機械的に検証可能にする。プライベートコーパスでは grounded な
  答えしか役に立たない。

## 4. いつグラフを使うか (判断表)

| シナリオ | 適切なツール |
|---|---|
| 単一文書 QA | RAG or 直接コンテキスト |
| 複数文書・単一ホップ | RAG + リランキング |
| 複数文書・マルチホップ | ナレッジグラフ |
| マルチエージェント共有状態 | ナレッジグラフ |
| 評価者に ground truth が必要 | ナレッジグラフ |
| 夜間ループ・永続メモリ | ナレッジグラフ |
| 単純な分類・ルーティング | 単一エージェント |

ルールオブサム: **chain (文書横断の事実連鎖) / share (構造化状態の共有) /
ground (追跡可能な証拠での判定) が必要ならグラフ。retrieve / classify
だけなら軽いツールで十分**。

なおコード領域では codegraph MCP が実質「事前構築済みナレッジグラフ」として
このパターンを既に体現している (シンボル = ノード、呼び出し = エッジ、
サブグラフ取得 = codegraph_explore)。

## 5. 運用の規律 (production readiness)

- **評価ハーネス**: gold set に対して「プロンプト変更 → スコアラー再実行 →
  F1 の動きを観察」。これがないとプロンプト変更が改善か劣化か知る術がなく、
  コーパス変化によるドリフトも検出できない。
- **監視シグナル4つ**: 抽出レート (急落 = ドメインシフト、急増 = 過剰抽出)、
  解決圧縮比、グラフ連結性 (孤島の増加 = 文書横断リンクの欠落)、
  クエリレイテンシ。
- **3つの standing practice**: ①毎日ランダムなノードを人間が読む (理解の
  腐敗防止) ②出荷前に抽出量の上限設定 (暴走コスト防止) ③スキーマをグラフと
  一緒にバージョン管理。
- 締めの観察: 「パイプラインは動いたら完成ではない。**任意の朝に、昨夜の
  生成物が正しかったかを言えるようになったら**完成」— 自律システム全般に
  適用される原則 (claude/CLAUDE.md §4 と同じ)。
